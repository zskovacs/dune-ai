## D. Complex Ability Findings

### Kwisatz Haderach

- Current engine support: DrawEffect, payment checks, once/game use and deterministic replay are reusable. Normal placement requires an unused Agent and matching icon, rejects full occupancy, moves one hand card, decrements unused count and adds an occupant. It cannot select/move an existing Agent or take this special turn with none unused.
- Missing capabilities: placement-source selection, ability-derived eligibility before the unused-Agent gate, selective access/occupancy policy, atomic relocation, Agent-kind provenance, destination bans/lifetimes and multi-card action context.
- Recommended implementation: a narrow typed special handler produces a single Agent placement plan for the existing validation/execution path. Select card/participants, source Agent if meaningful, destination/payment; validate without mutation; pay and commit exactly one placement/move; resolve card/space effects and draw; resume deployment/turn. A board-origin move does not decrement unused pool. Do not execute ordinary Place and then a relocation effect, which would send an extra Agent. Do not implement KH in this audit.
- Required rule exceptions: I p.13 permits KH with no supply Agents, moving an already-placed Agent and returning it to the same space; once/game High Council/Swordmaster and The Voice still apply. Voice lasts until the creator's next turn, not merely round end. I p.9 requires immediate board costs/requirements absent a verified exception. M p.14 establishes one Agent sent even with Graft/Ghola. Enforce that once in the action-level sending operation, rather than suppressing arbitrary copied effects.
- LegalActions implications: expose source/destination choices through the same GameAction hierarchy; offer the special turn with zero unused Agents when a legal completion exists. If staged, define cancellation/commit boundaries and avoid entries with no legal completion. Exclude selected origin during same-space occupancy evaluation, preserve once/game use, and never expose raw physical allocation IDs. Record choices/context for replay.
- Relevant source references: code `Turns/TurnEngine.cs` Validate/Place, `Turns/GameAction.cs`, `Runtime/BoardState.cs`; rules I pp.6,9,13 and M p.14. The complete draw1/any-space face is supplied by the user, not independently established as catalog data by the local KH clarification. Exact icon/occupied-destination permissions with additional own/enemy occupants require verified card/ruling evidence before enabling those cases; do not import Ix infiltration rules by analogy.
- Focused future tests: zero-unused relocation; same-space return; costs before rewards/draw; once/game and Voice retained; Voice expiry before creator's next turn; vacated Maker space; Agent kind; one send with KH+Graft/Ghola; illegal action hash/RNG/history immutability; replay at every suspended choice. Occupancy expectations remain evidence-gated. (I pp.9,13; M p.14.)

### Combat Intrigue

- Current engine support: explicit decision owner distinct from active turn, nested foreign choices, accepted-action replay, player Intrigue and shared IntrigueDiscard zones, primitive effects and preliminary strength. No Combat action/window/timing/reward executor exists.
- Missing capabilities: phase-aware LegalActions/Validate, no-normal-turn window ownership, clockwise eligibility/pass state, multiple plays per opportunity, child resolution returning to the same opportunity, distinct post-win/reward timing, marker refresh, typed Conflict rewards/outcome and continuation snapshot.
- Recommended decision flow: after all Reveal turns, open normal Combat priority from First Player; skip seats without troops; eligible owner plays one supported Intrigue at a time, resolves all children, and may play another before finishing their opportunity, or passes without playing. Playing clears consecutive-pass evidence. A previous passer can act on later rotation. After all current participants pass consecutively, establish outcome/rewards; allow sourced post-win plays and permitted reward interleaving; finish rewards/cleanup before Makers. I p.12 permits multiple cards per opportunity; do not rotate after every card.
- Required state-machine changes: add explicit Combat/Makers/Recall/Endgame/Completed phases; dispatch phase/window before TE's null-forgiving CurrentPlayerId read; generalize ContinueTurn into typed parent resumption; keep CurrentPlayerId nullable outside Agent/Reveal and DecisionOwnerId explicit. Proposed GameAction variants are PlayIntrigueAction, PassPriorityAction and FinishOpportunityAction; names are not current APIs. Window data needs kind/cursor/priority owner/played-in-opportunity/pass evidence/eligibility revision/continuation. An effect's child choices suspend priority rather than start another normal turn.
- Relevant source references: I p.12 for eligibility, order, passing, strength, post-win distinction, rewards/ties/troop returns; I p.13 for Demand Respect using spice rewards or To the Victor first. Code `Turns/TurnEngine.cs` LegalActions/Validate/ContinueTurn/NextPlayer; `TurnSnapshot.cs`, `GameAction.cs`, `CombatStrength.cs`. Post-win play cannot always occur before rewards because its costs may use them.
- Unresolved edge semantics: reevaluate public participation after effects; proposed conservative pass reset on membership change needs a sourced enabled-card scenario. The base PDF does not settle every removal/re-entry or simultaneous post-win ordering case. Preserve explicit gates rather than invent universal rules.

### Graft

- Current engine support: the pending list combines effects from card/space with individual source references, and physical card identity survives zone moves. This is a useful base, not Graft implementation.
- Missing capabilities: two-card Agent action, Graft traits/partner relationships, combined icons with provenance, executing vs copied-definition sources, if-grafted predicates, related-card targeting, delayed partner binding and one-sending-operation enforcement.
- Recommended implementation approach: prepare a participant group; ordinary Graft commits exactly two hand cards and one Agent placement, then enqueues each card/board effect with distinct sources in a player-order group. A Graft-specific handler can build that group, but needs the shared source/target/continuation model. Do not flatten effects or mutate shared CardRule to copy abilities. Copy self binds to the executing card; printed card identity/traits stay separate from copied box logic. Guard copy cycles.
- Required execution context: initiating player/card; participant physical references and roles/original zones; executing source; ability-definition source; paired-card bindings; decision owner, payer, recipient and typed target; action-group/turn ID; board space; timing and continuation. Add fields incrementally as their mechanics are implemented.
- Relevant source references: M p.10: exactly two cards, at least one Graft, either icon, both count as sending, player chooses card/board effect order. M p.11: if-grafted, partner reference, Ghola copy and Chairdog delayed return. M p.14: whole-box copying includes self-trash; copying does not copy Bene Gesserit identity; Ghola+Power Play remains 2 Influence; Ghola+Weirding Way allows two extra turns; Dispatch icons attach to selected participant; KH still sends one Agent; Usurp row participant is not in play and trash triggers can fire. X p.7: infiltration permission belongs only to marked icons. These exceptions require interaction fixtures, not a universal two-hand-card assumption for Usurp.

## E. Recommended Architecture

- Ability execution approach: **implemented** typed primitives/OptionalPayment/Choice and one TE resolver; **proposed** strict Sequence and PlayerOrdered causal groups, narrowly scoped typed predicates, semantic operations and dedicated special handlers only for actual exceptions. No natural-language card interpretation, scripting language, giant card-name switch or one class per trivial card.
- Rule modifier approach: **proposed**, independent queries for icon access/own and enemy occupancy/cost/requirements/ban/use limits. A KH placement plan holds transient permissions for one operation; future persistent abilities use immutable descriptors plus episode-owned usage/lifetime. ActiveEffect strings are not existing support. Voice needs next-creator-turn expiry (I p.13); Tech/Skills need round usage (X p.4; B p.4).
- Trigger/timing model: **implemented** acquire/Signet/board-Reveal dispatch; **proposed** typed occurrence/timing hooks whose children use the same continuation stack. Discard and trash are semantic operations, not every raw zone transfer; Unload can fire separately on discard and later trash of the same card (X p.7). Define only timing points required by enabled sourced content.
- Pending decision model: **implemented** list + option stack with AcquisitionDepth; **proposed** serializable frames separating chooser/payer/recipient/target and source provenance, preserving child-before-parent execution and typed resume destinations for Agent, Reveal, Combat opportunity, rewards and phases. Reuse one decision mechanism.
- Legal action integration: retain Candidates -> shared validation -> Step. Dispatch phase/window first; include every supported choice and exclude unsupported paths. Use incremental target/payment/participant selections to avoid Cartesian products. Auto-drain deterministic administration; preserve strategic ordering and Reveal purchase interleaving. Future action masks/structured encodings must be versioned and tied to explicit decision owner, not CurrentPlayerId. No RL encoder/algorithm is implemented.
- State mutation and safety: retain pre-mutation support checks; add construction-time graph validation and decision-time dynamic target/payment validation. Current preflight scans all optional/choice branches and may conservatively exclude otherwise legal paths. Current Step has no rollback: malformed duplicate SwordmasterEffect nodes are a source-traced example that could mutate then fail invariants; this trace was not executed as a new test. Validate permanent-operation constraints before commit. Hash every new cursor/frame/usage/lifetime/source; history-dependent trusted hash is not a search transposition key. Keep independent episode RNG; replay remains pinned-runtime, consistent with [Microsoft System.Random guidance](https://learn.microsoft.com/dotnet/fundamentals/runtime-libraries/system-random).
- Expansion compatibility: retain ADR0002's static module graph, replacement provenance and explicit interactions. Eventually lower verified executable capabilities once before gameplay. Runtime currently rejects expansions; no new expansion state is added now. Shared hooks cover Ix infiltration/Unload/Tech/dreadnoughts (X pp.4,6-7), Uprising Spy intelligence/recall/sandworms (U pp.10-11,14; S p.2), and Bloodlines conditional Skills/usage (B pp.4-5).
- Performance implications: existing candidate materialization, recursive per-candidate preflight, pending scans, per-Step full-card conservation and history allocate. No new measurement proves dispatch/modifier overhead dominant. Keep BCL records/collections and existing JSON/RNG. Compare explicit-frame vs baseline legal enumeration, depth 3 foreign decisions,3/4-player pass/play/resume, and 0/1/8 scoped modifiers using BenchmarkDotNet before optimization. Static rules compile once; mutable per-game state must not leak into shared definitions. Batched simulations remain independent and may be at different decision kinds/phases.

Representative expansion conclusions: Ix dreadnoughts affect participation/swords/returns/control, not just strength coefficients (X p.6); Uprising Gather Intelligence occurs immediately after placement before card/space effects and cannot reuse the same Spy paid for infiltration (U p.11); Imperial Privilege recalls another Agent, distinct from a Spy (S p.2); sandworms deploy directly, have restrictions and reward-doubling exceptions (U pp.10,14); owned Commander Skills are conditionally active and once/round, with recruitment from supply once/turn (B p.4). Command6+ needs Persuasion generated distinct from current spendable amount, and repeated Combat icons do not multiply the old-garrison allowance (B p.5). These are compatibility requirements, not implemented features.

## G. SLICE-004 Implementation Recommendations

**Combat, Round Completion & Endgame** should be divided into bounded tasks. Scope starts with unchanged original Imperium Standard competitive 3/4 players. Keep full authentic playability separate from engine-fixture completion.

1. **Prerequisite P1: causal execution and role context.** Extend `Turns/TurnSnapshot.cs` and TE Enqueue/Execute/Choose/ContinueTurn. Add typed sequence/order frames and explicit parent resumption; separate chooser/payer/recipient. Preserve existing meaningful effect order and Reveal purchase interleaving. Validate malformed permanent-operation graphs before mutation. Gate: focused tests for strict child priority, foreign beneficiary choices, nested acquire priority, failure immutability and replay. Run `mise run test:engine`.
2. **Prerequisite P2: phase/window dispatch.** Extend `Runtime/GameState.cs` phases; `Turns/GameAction.cs`, `TurnRules.cs`, `TurnSnapshot.cs`; TE LegalActions/SupportDiagnostics/Candidates/Validate/NextPlayer. Add shared-window state with nullable normal active player and explicit current owner. Gate: no null active-player dereference, no accidental NextPlayer on Combat child completion, supported legal/Step agreement and hidden-information tests.
3. **Sourced Combat definitions.** Add typed Intrigue timing and Conflict reward/outcome definitions under `Turns/`, plus complete verified entries in `OriginalImperiumTurnRules.cs` and `docs/rules-sources.md`. Reuse existing physical Intrigue/Conflict zones. Missing full faces remain Unsupported; synthetic fixtures may exercise architecture but cannot establish catalog completeness.
4. **Intrigue priority loop.** Implement I p.12's First-Player/clockwise, troop eligibility, multiple cards within one opportunity, pass/revisit, consecutive-pass reset, nested child/resume and strength refresh. Exclude post-win cards from ordinary priority. Explicitly resolve dynamic eligibility edge policy before enabling such cards.
