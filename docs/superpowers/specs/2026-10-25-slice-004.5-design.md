# SLICE-004.5 — Card Catalog & Ability Coverage Audit design

Status: approved by the user on 2026-10-25; executing the reviewed plan. No audit
inventory, tooling, runtime, catalog or future card batch is implemented by this
planning package. Approval covers this document and the companion
[implementation plan](../plans/2026-10-25-slice-004.5.md).

## Intent and scope

Establish a source-backed, machine-readable account of authentic content,
independent ability coverage, shared capability blockers and interaction risks.
Make the next content slices executable without repeating the SLICE-003.5/004
architecture audits. The detailed target is original Dune: Imperium (2020),
Standard competitive 3/4-player games. The first later expansion target remains
original Imperium + Rise of Ix + Immortality. Assess Ix, Immortality, Uprising,
Bloodlines, CHOAM and the Bloodlines Tech Module for source availability,
inventories, shared mechanics and dependencies; exhaustive expansion face
verification is outside this slice.

Incomplete source coverage is an acceptable **reported audit result**, not
permission to claim inventory completeness or authentic readiness. Every
discoverable original identity receives a record; undiscovered residual inventory
is represented by aggregate gaps, never fabricated card identities or effects.

## Selected approach and alternatives

Author one independent JSON inventory at `docs/content/coverage/inventory.json`.
Keep it outside embedded runtime catalogs and do not load it during gameplay.
Use Python 3.12 standard-library dataclasses/enums, `json`, `pathlib`, `argparse`
and hashing for a small offline typed loader/validator/report tool. This is audit
authoring infrastructure, not Python game logic. Existing pytest verifies tooling;
one focused xUnit test file compares registry assertions with actual C# objects
using System.Text.Json. No C# source parser, extra project, database, package,
global tool or general schema interpreter is needed.

The schema is the explicit typed model in `scripts/content_coverage_model.py`,
documented in `docs/content/coverage-schema.md`. JSON Schema plus a new validation
dependency is unnecessary for this bounded authoring contract. Do not claim full
JSON Schema conformance. Reject unknown fields/values instead of silently
accepting misspelled metadata. Ordinary targeted validation is permitted; do not
build a reusable validation framework.

Alternatives rejected: extending `ContentDefinition` (changes canonical runtime
identity and confuses audit/execution); manually synchronized Markdown tables (drift); CSV (poor nested evidence/ability
relationships); a full external dataset
import (unverified rights/semantics); runtime text parsing or a new effect language (out of scope). These are
author-selected decisions offered for approval.

## Canonical inventory contract

Top-level `schemaVersion` is `dune-content-coverage-v1`; `auditRevision` and
`repositoryRevision` identify audit/source snapshots independently of game
versions. Collections are `sources`, `expectations`, `content`, `capabilities`,
`interactions`, `batches` and `configurations`. IDs are globally unique within
their explicit namespaces. References are IDs, not repeated free-text tables.

| Record                  | Required responsibilities                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
|-------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Source / evidence claim | Exact document or URL/revision, one-based page or external locator, products/categories, evidence type, completeness, verification, rights, discrepancies and acquisition limits. Local PDF hashes/page bounds are pinned; external sources are never required by CI.                                                                                                                                                                                                                                                            |
| Inventory expectation   | Product/edition/category/tier, expected boxed copies and known unique count or null, unit/basis, scope and evidence. Residual missing copies are distinct from unknown unique-definition counts.                                                                                                                                                                                                                                                                                                                                 |
| Content                 | Existing `ContentId` where present; otherwise same product/category/component/version convention plus explicit edition and variant lineage. Name, owning product/category, nullable boxed quantity, nullable per-player recipe count, availability/replacement/exclusion references, identity/quantity evidence, discovery status, semantics completeness and independent abilities. Board IDs reuse exact setup `BoardSpaceId.Value`; other components use scoped audit IDs explicitly distinguished from runtime registration. |
| Ability                 | Stable `contentId#slot:key` ID, typed slot/timing/classification; concise semantic claim; typed precondition/cost/choice/role/usage descriptors; evidence refs; required capability/interaction IDs; implementation/test refs; support, blockers, exclusions and one primary planned batch. Unknown text is explicit, never an empty known effect.                                                                                                                                                                               |

| Configuration           | Exact base/expansions/modules/mode/seats/leader policy; composition evidence; computed inventory/ability/interaction gates and explicit initialization/full-game/RL validation evidence. Slots include Setup, Passive, Agent, Reveal, Acquire, SignetRing, Intrigue,
Combat, PostWin, Endgame, Triggered and PersistentModifier. Once-per-turn/round
is a usage restriction, conditional is a descriptor, not a mutually exclusive
slot. A multi-effect printed box is one ability with children/descriptors;
separately timed independent abilities receive separate IDs. Printed absence of
a box/effect is `verified-absent`, excluded from ability denominators; a known
box with unreadable semantics remains unresolved. Record whole-face/slot
discovery completeness so empty ability lists cannot imply completeness.

Use independent dimensions:

- Discovery: `not-discovered`, `discovered`.
- Sourcing: `unsourced`, `partially-sourced`, `fully-sourced`.
- Verification: `unverified`, `verified`, `disputed`.
- Classification: `primitive`, `composite`, `special`, `unresolved`.
- Implementation: `not-implemented`, `partially-implemented`, `implemented`,
  `unsupported`; unsupported identifies an explicit current engine boundary.
- Validation: `not-tested`, `tested`; refs describe behavioral, integration,
  privacy/replay or inventory evidence and never equate these kinds.
- Blockers: structured open/resolved records, scope and reason; `blocked` is
  derived from open blocking dependencies, not an incompatible linear status.

An implemented primitive does not implement every ability requiring it. Full
ability support requires complete verified semantics; implemented timing,
cost/precondition/choice/role behavior; LegalActions/Step integration; applicable
interaction support; privacy/replay safety and meaningful behavioral evidence.
Historical test refs can support existing claims but must be labeled historical
until rerun. Report known-ability counts with unknown-slot/undiscovered-identity
counts alongside; never calculate a whole-game percentage from a partial list.

## Dependency analysis, batches and readiness

Represent `Content → Ability → Capability → implementation references`, with
interaction blockers and prerequisite batches linked by ID. Missing shared
mechanics appear once and list their dependent abilities. Keep capability and
batch prerequisite graphs acyclic; interaction relationships need not be a DAG.

Seed interaction analysis from existing findings: KH/Voice/Signet; Combat and
post-win payments; conditional Influence, selected trash/discard, opponent roles;
Ix infiltration/Unload/Tech/dreadnoughts; Immortality Graft/Ghola/research/genetic
markers/acquisition; Uprising Spy/intelligence/recall/sandworm/Shield Wall/reward
doubling; Bloodlines Skills/usage/recruitment/Tech. Preserve source gates for
Alliance-holder loss below four, tied shared Intrigue draws, contested Mentat,
condition-dependent Influence, finite-stock choices, Plot, unknown post-win faces
and interacting Endgame ordering unless trustworthy clarification resolves them.
New rulings are documented proposals for later implementation, not runtime fixes.

Order future batches lexicographically by mandatory original authenticity blocker,
dependency order, shared-mechanic reuse/dependent-ability count, reliable evidence,
then complexity/determinism/privacy/architecture risk. Use high/medium/low bands
and explain tradeoffs; do not manufacture effort estimates from card count.
Start with starter/real-leader path and missing board operations, then primitive
and basic composite Imperium groups, official Conflict/Combat, other Intrigues
and isolated special mechanics, then authentic validation. Adjust the order to
the actual graph. Split ordinary work into roughly 10–20 related definitions
where appropriate, with much smaller special-handler/leader tasks. These are
backlog deliverables, not authorizations to implement those abilities here.

Readiness separately reports recognized vocabulary, structurally validated
composition, reconciled selected inventory, supported abilities, verified reachable
interactions, authentic initializer, authentic deterministic games and RL
eligibility. Evaluate original Standard 3p and 4p separately, original+Ix and
original+Ix+Immortality (each with explicit 3/4-seat applicability). Policy-specific
leader subsets cannot imply full random/all-leader support. Missing/unknown
reachable content fails closed. A synthetic terminal episode satisfies none of
the authentic gates. RL eligibility additionally needs legal-action completeness,
privacy/invalid-action/replay checks, reproducible authentic episodes and a
documented supported environment boundary; this slice adds no RL adapter.

## Validation and generated documentation

Validation checks strict types/required fields/unknown members, unique content and
ability IDs, product/edition/category applicability, valid references and paths,
source page bounds/hash identities, quantity basis/totals/tier reconciliation,
duplicate/version conflicts, dependency cycles, meaningful blocker reasons,
noncontradictory status/evidence combinations and batch membership. Unknown or
incomplete data is valid when explicitly recorded; unexplained mismatches are
errors. A separate readiness result remains false for such data. All checks are
offline and deterministic, without runtime source resolution, reflection or card
text interpretation. Missing optional local PDFs produce an explicit unavailable
evidence diagnostic; do not require committing copyrighted sources to pass CI.

The tool produces stable generated report regions in `inventory-audit.md`,
`ability-coverage.md`, `interaction-matrix.md`, `implementation-batches.md` and
`readiness-gates.md`; prose outside regions explains methodology/risks only.
`content:report` updates regions; `content:validate` validates and detects stale
reports without writing. Stable ordering/newlines and no clock fields make a
second generation byte-identical. Counts/graph membership come only from JSON.
`sources.md` holds source-quality analysis, with quantitative summaries generated
where repeated; `coverage-schema.md` documents the contract. ADR0007 records the
offline boundary, rights/evidence model and versioning consequences.

Use focused pytest tests for malformed input, totals/gaps, dependency/status
failures, deterministic/stale reports and readiness false positives. Add
`ContentCoverageRegistryTests` to the existing engine test project: inspect
`ContentCatalog`, `OriginalImperiumTurnRules.Create()` and `.CreateLifecycleRules()`
objects and reconcile all authored identities/slots and explicit unsupported
markers. Assert test fixtures cannot count as official coverage. This test is a
drift guard, not proof of printed semantics or gameplay correctness.

Add mise tasks `content:validate`, `content:report`, `content:test` and
`content:registry`; make `check` depend on content validation. Existing pytest
discovery and .NET suites pick up the new tests. Run the focused tasks, then
`mise run check`, `mise run smoke`, both 3/4-seat synthetic lifecycle previews
and `git diff --check`. No benchmarks are necessary for offline-only changes.
Keep existing pins/locks unchanged. No mandatory TDD or failing-test proof.

## Architecture, performance and state safety

Do not change production code, embedded JSON, support flags, canonical bytes or
runtime contracts in this slice. A demonstrated need outside this boundary
requires a concrete plan amendment and user review before implementation.
Future batches resolve immutable definitions once, use existing typed dispatch
and shared candidate/Step validation, and measure larger decks, branch shapes,
modifier queries and authentic complete games before optimization. Existing
synthetic benchmark costs are historical evidence, not authentic throughput.

Backlog validation must preserve generated-child preflight (SLICE-004 F1),
mandatory reservations, nested child-before-parent execution and rejection
without RNG/history/state mutation. Identify actual affected card families,
not a speculative generic feasibility solver. Flag new selected targets, hidden
conditions, usage/lifetime, placement provenance, copy bindings and turn scheduling
for legal-action/state/replay/privacy changes. No opponent hidden identities,
deck ordering, RNG, privileged execution context, physical allocation IDs or
private support metadata enter policy observations/actions.

ability accounted for, original expected totals reconciled or quantified as
gaps, expansion source/mechanic availability assessed, synthetic data excluded,
dependencies/interactions/batches/readiness maintainable from the canonical data,
all task/final reviews closed, and actual required checks passing. Neither audit
metadata validation nor old full-game fixtures establishes authentic readiness.

Explicit exclusions: mass card/leader/Conflict/Intrigue implementation, KH/Graft/
Ghola/expansion gameplay, new resolver/DSL/text interpreter, RL/interop/search,
database/service/UI, restricted scraping/imports and unrelated optimization.

Content records also carry typed `authenticity` (`official` or `synthetic`).
Synthetic records used by tooling fixtures never contribute to authentic counts.
